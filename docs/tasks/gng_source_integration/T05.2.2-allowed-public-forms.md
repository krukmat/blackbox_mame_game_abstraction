# T05.2.2 - Allowed Public Forms

## Status

Completed

## Purpose

Define which public forms may remain in harness public metadata without violating the clean-room public-output boundary.

## Allowed Public Forms

### A1. Opaque private evidence handles

Allowed form:

- `private://<run-id>`
- `private://<run-id>/<sanitized-suffix>`

Why allowed:

- they preserve traceability without disclosing filesystem structure
- they do not reveal local machine paths or ROM locations

Applicable fields:

- `private_evidence_ref`
- `command[*]` after path redaction

### A2. Abstract, non-path scalar metadata

Allowed form:

- run identifiers
- booleans
- counts
- enum-like statuses
- numeric measurements

Examples:

- `run_id`
- `frame_plan_length`
- `dry_run`
- `runner_status`
- `preflight.detected_version`
- `execution.returncode`

Why allowed:

- these values do not expose local filesystem structure or private evidence paths

Applicable fields:

- any public metadata field carrying non-path scalars

### A3. Repo-safe relative references

Allowed form:

- relative references that point to repo-owned helper assets or code paths and do not expose private evidence or ROM storage

Current example:

- `scripts/mame_autoboot.lua`

Why allowed:

- the value is repo-relative, public, and not tied to private evidence or local ROM placement

Constraint:

- this is allowed only when the relative path refers to a public repo asset and does not resolve to a blocked sensitive class from `T05.2.1`

Applicable fields:

- `command[*]`

### A4. Human-readable messages that are path-free after sanitization

Allowed form:

- explanatory messages that remain understandable after sensitive paths are removed or replaced

Examples:

- validation messages that refer to a missing ROM input without embedding the machine-local path
- execution messages that describe failure class without exposing local directories

Why allowed:

- public metadata may retain operational meaning as long as it does not disclose local sensitive paths

Applicable fields:

- `preflight.issues[*].message`
- `execution.stdout`
- `execution.stderr`
- future string fields in public runtime metadata

Constraint:

- these strings are only allowed if they are path-free or contain only allowed opaque handles

### A5. Public repo documentation and schema references

Allowed form:

- public repo paths or identifiers that point to tracked docs, specs, or schema assets and do not disclose local private execution details

Why allowed:

- these are part of the public repo contract, not private machine state

Constraint:

- this form is allowed only for explicitly public repo resources
- it is not a blanket allowance for arbitrary workspace-relative paths

Applicable fields:

- future public metadata fields, if needed

## Not Automatically Allowed

The following class is not automatically permitted even if it is not private evidence:

- `S6 Non-private workspace path in public runtime payload`

Policy:

- it must be evaluated case by case
- it is allowed only when it clearly points to a public repo-owned resource and carries no local machine or ROM-location disclosure

## Allowed-Form Summary By Field

- `command[*]` may contain:
  - abstract arguments
  - non-path scalars serialized as strings
  - repo-safe relative references
  - opaque `private://...` handles

- `preflight.issues[*].message` may contain:
  - path-free human-readable explanations
  - opaque handles if needed

- `execution.stdout` and `execution.stderr` may contain:
  - path-free human-readable output
  - sanitized text that preserves operational meaning without leaking local filesystem details

## Boundary Rule

A public value is allowed only if at least one of the following is true:

1. it is abstract and non-path-bearing
2. it is an opaque handle defined by policy
3. it is a repo-safe public relative reference
4. it is a human-readable string that remains path-free after sanitization

If none of those are true, the value is not allowed and must be classified by `T05.2.3` as blocked or by `T05.2.4` as replace-only.
