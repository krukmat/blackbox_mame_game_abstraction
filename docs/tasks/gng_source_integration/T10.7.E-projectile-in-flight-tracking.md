# T10.7.E — Projectile In-Flight Tracking Calibration

## Status

🔲 Planned — approved as the follow-up to T10.7.D Option B.

## Parent Task

[T10.7 — Tracker Continuity Fix](./T10.7-tracker-continuity-fix.md)

## Objective

Replace the surrogate `projectile_velocity_x` values with a real measurement derived from projectile motion across frames. Build the minimum continuity and picker workflow needed to measure projectile x displacement in flight and propagate the resulting value into the public calibration and mechanics artifacts.

## Scope

- Define a calibration-scoped projectile continuity path for consecutive frames
- Implement projectile trajectory candidate extraction from observed motion regions
- Implement `apps/mame-harness/projectile_trajectory_picker.py` following ADR-019
- Produce private candidate output under `evidence/private/run_<id>/logs/`
- Support user accept/reject validation of projectile trajectories
- Compute calibrated `projectile_velocity_x` from accepted trajectories
- Update:
  - `specs/calibration/gng_physics_calibration.yaml`
  - `specs/mechanics/gng_abstract_mechanics.yaml`
- Remove surrogate wording once a real value is written
- Update T10.7 parent tracking docs when complete

## Out of Scope

- Generic enemy continuity
- Full public trace schema redesign
- Projectile acceleration or gravity modelling
- Combat/balance tuning in RN
- T11.4 scene work

## Dependencies

- ✅ T10.7.A — jump/gravity calibrated
- ✅ T10.7.B — duplicate player collision fixed
- ✅ T10.7.D — Option B selected; ADR-020 accepted
- Prefer running after T10.7.C so locomotion sync is not mixed with projectile work
- Requires a capture with enough visible projectile flight frames; may reuse an existing run only if it contains sufficient fire events and clean projectile visibility

## Evidence Assessment

Existing evidence was inspected during T10.7.E implementation:

- `run_t10_7_walk` has no fire input in its expanded input plan. Projectile trajectory candidates from this run were false positives from player movement and were rejected by the operator.
- `run_e18611b8a7e7` includes fire inputs and produced trajectory candidates, but the operator reviewed the first candidate groups and observed Arthur death / non-projectile motion rather than visible in-flight projectiles.

Conclusion: existing evidence is not sufficient for accepted projectile calibration. Do not continue reviewing the current candidate sets unless a later manual inspection proves a candidate is a visible projectile. The next step is a new projectile-specific capture.

Minimum new capture requirement:

- Boot to controllable gameplay.
- Keep the player on stable ground and avoid death/enemy overlap during the sample window.
- Fire at least 5 separated shots while the player is idle or moving minimally.
- After each fire input, hold no input for at least 20 frames so the projectile remains visible without player-motion contamination.
- Prefer a clear horizontal lane with no nearby enemies or large moving sprites.
- Capture at least 3 visually valid projectile trajectories with 4+ consecutive visible frames each.
- Run `projectile_trajectory_picker.py` on the resulting public numeric trace and accept at least 3 operator-confirmed candidates before updating public calibration artifacts.

- Requires careful separation between private evidence inspection and public artifact output

## Acceptance Criteria

1. A projectile tracking approach is implemented with deterministic matching rules documented in code
2. `apps/mame-harness/projectile_trajectory_picker.py` exists and follows ADR-019 contract
3. Picker stdout contains only frame numbers and numeric metadata — no private paths
4. Picker writes `evidence/private/run_<id>/logs/projectile_trajectory_candidates.json`
5. User accepts at least 3 valid in-flight projectile trajectory candidates
6. `projectile_velocity_x` is computed from accepted projectile x displacement data, not player movement
7. `specs/calibration/gng_physics_calibration.yaml` reflects the real measured value and documents the actual source method
8. `specs/mechanics/gng_abstract_mechanics.yaml` matches the calibration YAML
9. Surrogate inconsistency (`0.1871/s` vs `8.5348/s`) is removed
10. Regression tests cover trajectory matching and picker output contract
