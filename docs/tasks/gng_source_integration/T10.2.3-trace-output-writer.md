## Purpose

Serialize the `list[TraceEntry]` produced by T10.2.2 to a public JSON file, applying `ensure_public_output_path` and `ensure_no_private_paths` before writing. Connect the extraction pipeline to the CLI as a new `extract-trace` subcommand without weakening the clean-room boundary.

## Reference Reasoning

`Medium`

Reasoning basis:

- Recataloging from `Low` to `Medium` is explicit.
- The previous catalog assumed a pure writer task. Code inspection shows one additional integration decision is required: `run_id` alone is not enough to reconstruct the semantic `InputPlan`, so the CLI contract must carry the input plan path explicitly or add a new recovery layer.
- `trace.schema.json` currently describes a single `TraceEntry`, while `load_trace_entries` and the planned output format use a wrapped payload (`{"trace": [...]}`). That mismatch must be handled deliberately in scope rather than treated as a mechanical schema-validation step.
- The task writes a public artifact and therefore touches the private/public boundary governed by ADR-003 and ADR-008.

## Current State Analysis

- `packages/validation/behavioral_diff.py` already contains the canonical `TraceEntry` dataclass, `load_trace_entries`, and the existing public writer pattern (`write_validation_reports`), but it does not yet expose a trace writer.
- `apps/mame-harness/vision_pipeline.py` stops at entity-candidate generation. There is no current run-level pipeline that goes `FrameManifest -> FrameDiffer -> extract_trace -> public JSON`.
- `apps/mame-harness/cli.py` has no `extract-trace` subcommand.
- `packages/schemas/trace.schema.json` is an entry schema, not a file-wrapper schema. A payload shaped as `{"trace": [...]}` cannot be validated against it as-is.
- `apps/mame-harness/input_planner.py` can load YAML plans and export a private flat JSON for Lua input injection, but that exported JSON does not preserve the original action labels needed to reconstruct an `InputPlan` safely from `run_id` alone.

## Scope

- implement `write_trace_output(entries: list[TraceEntry], output_path: Path) -> Path` in `behavioral_diff.py`
- output format: `{"trace": [{...TraceEntry fields...}, ...]}` to align with `load_trace_entries`
- apply `ensure_public_output_path(output_path)` and `ensure_no_private_paths(payload)` before write
- add a run-level helper in `vision_pipeline.py` that:
  - loads the private frame sequence for the run
  - diffs consecutive frames
  - loads the provided YAML input plan
  - calls `extract_trace(...)`
  - writes the public trace through `write_trace_output(...)`
- add `extract-trace --run-id <id> --input-plan <path> --output <path>` subcommand to `cli.py`
- TDD: tests for writer guardrail enforcement, round-trip loading, pipeline integration, and CLI subcommand

- changing the `extract_trace(diff_stats, input_plan)` contract from T10.2.2.4
- introducing a new JSON Schema validation dependency
- defining a new top-level wrapper schema for trace files

## Implementation-Blocking Ambiguities

None, if the approval accepts the two contract clarifications below.

1. CLI contract clarification:
`extract-trace` must require `--input-plan`.
`run_id` does not currently provide enough information to reconstruct a semantic `InputPlan` object safely.

2. Schema validation clarification:
T10.2.3 should verify writer round-trip compatibility and per-entry contract shape.
Formal validation of the wrapped file against a dedicated wrapper schema is not currently possible because `packages/schemas/trace.schema.json` defines a single entry object, not `{"trace": [...]}`.

## Approval Recommendation

Approve T10.2.3 with the clarified implementation contract below:

1. Keep the writer colocated with `TraceEntry` and `load_trace_entries` in `packages/validation/behavioral_diff.py`.
2. Reuse `apps/mame-harness/vision_pipeline.py` for end-to-end extraction instead of introducing a new top-level module.
3. Require `--input-plan` on the CLI rather than trying to reverse-engineer action semantics from the private exported JSON.
4. Treat T10.2.3 as a guardrail-aware serialization and integration task.
5. Leave formal file-level schema validation to T10.4 or to a future wrapper-schema task if that becomes necessary.

## Exit Decision

- `T10.2.3`: ready for implementation approval with the clarified scope above
- next blocking task after approval: implementation of writer + pipeline + CLI wiring
- downstream tasks relying on this output remain `T10.3` and `T10.4`
