# T05.2.5.1 - Policy Artifact Cross-Check

## Status

Completed

## Purpose

Cross-check `T05.2.1` through `T05.2.4` to identify aligned decisions, omissions, or contradictions before surface-level consistency review.

## Aligned Points

### 1. The policy is class-first, not module-first

All artifacts consistently treat policy in terms of:

- sensitive value class
- affected public field
- public handling rule

This matches the conclusion of `T05.2.1` and is preserved in `T05.2.4`.

### 2. Private evidence paths are never public as raw paths

The following artifacts align on this point:

- `T05.2.1` identifies private evidence paths as `S1`
- `T05.2.2` allows only opaque `private://...` handles
- `T05.2.3` blocks raw private evidence paths
- `T05.2.4` marks them as `replace` across public runtime fields

### 3. ROM paths and absolute local paths are non-public

The following artifacts align on this point:

- `T05.2.1` identifies direct ROM paths as `S4` and absolute local paths as `S5`
- `T05.2.2` does not allow them as public forms
- `T05.2.3` blocks them explicitly
- `T05.2.4` marks them as `replace` wherever operational meaning may remain

### 4. Human-readable messages are only allowed after sanitization

The following artifacts align on this point:

- `T05.2.2` allows path-free messages only
- `T05.2.3` blocks unsanitized validation and process messages
- `T05.2.4` marks message-bearing fields as `replace`

### 5. Repo-safe relative references are opt-in, not default

The following artifacts align on this point:

- `T05.2.1` identifies workspace-relative runtime paths as `S6`
- `T05.2.2` allows only explicitly repo-safe relative references
- `T05.2.3` blocks non-approved workspace-relative paths by default
- `T05.2.4` gives `S6` the only mixed rule: `allow or replace`

## Tensions Or Clarifications Needed

### 1. `S3 Crop path` is blocked in `command[*]` even though the audit does not currently show crop paths there

Assessment:

- this is not a contradiction
- it is a conservative policy choice

Why it is acceptable:

- `T05.2.3` defines what must never be public, not only what has already been observed
- `T05.2.4` correctly encodes that conservative rule

### 2. `S6 Non-private workspace path` needs explicit case-by-case handling in implementation

Assessment:

- this is the main policy nuance, not a contradiction

Why it matters:

- `T05.2.2` allows some repo-safe relative paths
- `T05.2.3` blocks non-approved workspace-relative paths by default
- `T05.2.4` therefore must use `allow or replace` for `S6`

Implementation implication:

- `T05.3` must implement a positive allowlist or equivalent explicit check for repo-safe references, not an open-ended relative-path allowance

### 3. `F6 Any public metadata payload written through write_public_metadata` is represented indirectly in `T05.2.4`

Assessment:

- this is a mild abstraction gap, not a contradiction

Why it matters:

- `T05.2.1` includes `F6` as the last public-output gate
- `T05.2.4` focuses on runtime-facing fields such as `command`, `preflight`, and `execution`

Resolution:

- treat `T05.2.4` as the canonical field-level runtime matrix
- treat `F6` as an enforcement obligation for `T05.3` and `T05.4`, not as a separate policy exception

## Cross-Check Conclusion

The four artifacts are materially aligned.

No direct contradiction was found between:

- the sensitive-class inventory
- allowed public forms
- blocked public forms
- the redaction decision table

The main implementation-sensitive nuance is `S6`, where relative repo-safe references are allowed only through explicit opt-in treatment.

## Ready State For Next Review

`T05.2.5.2` can proceed using this cross-check result without reinterpreting the four policy artifacts.
