## Objective

Produce a reliable `locomotion_velocity_x` measurement using a controlled walk-only MAME capture and the ADR-019 human-validated picker pattern. The existing two values are mutually inconsistent and both come from unreliable sources. This task replaces both with a direct kinematic measurement from stable flat-ground walking segments confirmed by the operator.

## Reasoning Grade

`Medium`

Reasoning basis:
- Follows the established ADR-019 pattern — picker design is well-defined
- New picker module (`walk_segment_picker.py`) must be designed correctly: walking segments have no natural "peak" anchor like jumps, so the algorithm must detect stable velocity runs differently
- Consistency gate logic (std_dev check) is novel relative to the jump picker — requires careful reasoning about what "stable walking" looks like in the trace

- Walk-only capture session required (user action)
- Three file updates (calibration YAML, mechanics YAML, PhysicsSystem.ts)

**Owner: User**

1. Agent runs: `./scripts/launch_manual_capture_autoboot.sh t10_7_walk`
2. Once Arthur is controllable (~frame 1505):

### ST.C3 — Implement `walk_segment_picker.py`

**Owner: Agent**

**Governing ADR:** [ADR-019](../../adr/ADR-019-human-validated-calibration-candidates.md). Same three-phase contract as `visual_jump_picker.py`.

Create `apps/mame-harness/walk_segment_picker.py`:

- **Input**: `run_id` (CLI positional argument)
- **Reads**: `specs/traces/gng_trace.json`
- **Algorithm**:
  1. Read consecutive `entity_id == "player"` entries from the public trace
  2. Detect locomotion steps from horizontal displacement rather than trusting `walking_*` state labels alone:
     - frame gap within a short tolerance window so brief missing/idle spans can still be bridged
     - `|Δx|` within a bounded locomotion band (reject near-zero noise and teleport-sized jumps)
     - `|Δy|` small enough to stay on flat ground
  3. Group consecutive valid steps sharing the same inferred direction (`left` / `right`)
  4. Drop segments with `frame_count < 5`
  5. Per-segment: compute `Δx_i = |x[i] - x[i-1]| / Δframe_i` for each consecutive frame pair
  6. Per-segment metrics:
     - `velocity_x_median = median(Δx_i)`
     - `velocity_x_std = std(Δx_i)`
     - `consistency_ok = (velocity_x_std / velocity_x_median) < 0.30` (drop division-by-zero if median==0)
- **Outputs**:
  1. Stdout: table with columns `id | direction | start_frame | end_frame | frames | v_median | v_std | y_span | consistency_ok`
  2. Side effect: `evidence/private/run_<id>/logs/walk_candidates.json`
  3. Path instruction at top: "Open `evidence/private/run_<id>/frames/extracted_png/<NNNN>.png` to inspect any frame."

**Unit tests** (in `apps/mame-harness/tests/test_walk_segment_picker.py`):
1. `test_segment_detection_groups_consecutive_walking_frames`
2. `test_segment_too_short_is_dropped` — frame_count < 5
3. `test_consistency_gate_passes` — low std_dev → `consistency_ok=True`
4. `test_consistency_gate_fails` — high std_dev → `consistency_ok=False`
5. `test_output_contains_no_private_paths` — stdout mock check (ADR-019 / ADR-006)

**Files affected:** `apps/mame-harness/walk_segment_picker.py`, `apps/mame-harness/tests/test_walk_segment_picker.py`

## Risks

- **R1 — Too few walking frames in trace**: If Arthur was on-screen walking for < 100 frames, segments will be short. Mitigation: record 2–3 short left–right cycles as instructed in ST.C1 so the picker can aggregate multiple clean segments even under early enemy pressure; incidental jumps are acceptable outside the accepted segments.
- **R2 — Inconsistent Δx due to screen-space normalization**: The trace stores x as a fraction of frame_width. As long as width is constant (256px for GNG), Δx in normalized units is proportional to real velocity. No correction needed.
- **R3 — Segments rejected by consistency gate due to bounding-box jitter**: The vision layer measures bounding-box center, not sprite anchor. Natural jitter in the box may inflate std_dev. If all segments fail the 0.30 gate, relax threshold to 0.50 and note the constraint.
- **R4 — New moveSpeed breaks RN engine tests**: Tests assert `moveSpeed ≠ hardcoded stub value`. Adjusting the threshold is acceptable; deleting is not.
