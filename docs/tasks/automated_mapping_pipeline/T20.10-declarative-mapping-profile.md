# T20.10 — Declarative Per-Game Mapping Profile

## Objective
Bind the experiment battery, optional memory addresses, and confirmed archetypes into a single
declarative per-game "mapping profile", so onboarding a new MAME title is configuration rather
than bespoke CV engineering.

## Scope
- A `mapping_profile` schema in `packages/schemas/` referencing: source profile (ADR-005),
  experiment battery plans (T20.3), optional cheat-DB address config (T20.5), vision config
  (T20.7/8), and archetype confirmations (T20.9).
- A driver command that, given a mapping profile, runs the battery, calibrates, extracts the
  trace, and emits the public mechanics artifacts end to end.
- Migrate GNG to a mapping profile as the reference instance.

## Out of scope
- Adding a second concrete game (this only makes it possible).

## Dependencies
T20.3, T20.4, T20.9 (and T20.5/T20.7/T20.8 where present).

## Reasoning grade
High — cross-module orchestration; the generalization contract.

## Effort grade
Medium.

## Acceptance criteria
- GNG end-to-end runs from a single mapping-profile invocation.
- The profile contains no game-specific code branches (contrast ADR-005 Known Gap: hardcoded
  `if profile_id == "gng"`); game specifics live in config.
- A documented checklist exists for onboarding a new title via a new profile.
- All outputs still pass guardrails.

## Recommended model
Opus.

## Reference documents
- `docs/plans/automated_mapping_pipeline_plan.md`
- ADR-005 (source profile), ADR-009, ADR-024, ADR-026, ADR-025, ADR-027
- `apps/mame-harness/source_profiles.py`, `apps/mame-harness/cli.py`, `packages/schemas/`

## Agent handoff prompt
"Define a declarative mapping_profile schema binding source profile + experiment battery +
optional addresses + vision config + confirmed archetypes, and a single driver command that
produces the public mechanics artifacts end to end. Migrate GNG to it as the reference and
write a new-game onboarding checklist. No per-game code branches."
