# T10.7.A — Visual-Anchored Calibration (Plan)

## Status

Proposed — supersedes T10.7 ST3 + ST4 if approved. Awaiting explicit approval before implementation.

## Objective

Produce trustworthy `jumpVelocity_y` and `gravity_y` constants for `PhysicsSystem.ts` by anchoring physics calibration on user-confirmed peak frames from a controlled jump-only capture, bypassing the residual tracker entity-id-collision noise observed at the end of ST3.

## Why This Pivot

ST1 (`max_frame_jump_px`) and ST2 (`MIN_GROUND_STREAK` debounce) reduced `jump_start` event clustering from **174 → 30**, but the gate of `< 30` remained unmet by one event. Diagnostic on the regenerated trace surfaced a deeper residual source:

- 85 frames in the regenerated trace have **two entries with `entity_id="player"`** in the same frame
- Root cause: `_entity_id_from_type` in `trace_extractor.py` returns `"player"` for any blob whose area ratio ≥ `_RATIO_PLAYER`, even blobs that `find_arthur` did NOT claim as Arthur
- Effect: a second "player" entity tracks its own state history → emits its own `jump_start` events independent of the debounce counter
- Each extra "player" entity adds spurious `jump_start` events through the input-injection Rule 4 path

Fixing this residual source requires a deeper change to the entity-id resolution path — refusing `entity_id="player"` to non-Arthur blobs entirely. This is an architectural change with wider impact (touches multi-entity tracking and downstream consumers) than ST1/ST2's contained additions.

**Alternative path**: anchor calibration on a small set of user-confirmed peak frames from a dedicated jump-only capture. This:

1. Bypasses the entity-id-collision entirely — we only need accurate y-values at a handful of frames, not a globally clean trace
2. Produces calibration values with explicit human ground truth
3. Defers the entity-id-collision fix to a separate task (`T10.7.B`, future)
4. Unblocks T11.4 faster (the original goal of T10.7)

## Amendment 2026-05-23 — Candidate detection mechanism

**Original ST.A3 design assumption (incorrect)**: read `evidence/private/run_<id>/logs/input_plan.json` to find user's jump button press frames.

**Actual behavior discovered**: `input_plan.json` records only the **planned** inputs (autoboot sequence: coin + start). User keyboard inputs during manual capture go directly to MAME but are NOT logged in the input plan. Verified: 11504-frame input plan from `run_t10_7_jumps` contains 0 user button presses post-boot.

**New ST.A3 mechanism**: detect jump candidates by running peak-detection on the player y-coordinate signal in the regenerated `gng_trace.json`. Each local minimum (Arthur at maximum height — recall y=0 is top of screen) is a candidate jump peak. Adjacent grounded frames provide jump_start and land anchors.

### Why this aligns with ADR-001 (and is governed by ADR-019)

ADR-001 establishes the principle: *"Enforcement must be structural, not advisory."* It applies this to private/public path discipline by codifying `ensure_no_private_paths()` rather than relying on documented conventions.

The amended ST.A3 applies the same principle to the calibration protocol:
- **D-style manual scrolling** = advisory enforcement (workflow lives in docs; humans execute it ritually)
- **C-style peak detection + structured candidate validation** = structural enforcement (workflow lives in `apps/mame-harness/visual_jump_picker.py`; humans validate within a bounded contract)

The pattern is formalized in **[ADR-019 — Human-Validated Calibration Candidates Pattern](../adr/ADR-019-human-validated-calibration-candidates.md)**. This task is the **first instantiation** of that pattern. The picker tool must conform to ADR-019's three-phase contract:

```
public trace → picker (machine) → human accept/reject → downstream calculator
```

**Multi-mechanic scope**: ADR-019 is explicitly designed for multiple future picker tools beyond this task's jump-specific scope. See ADR-019 section "Future scaling — anticipated picker instances" — anticipated next instances are `visual_locomotion_picker.py` (walking speed) and `visual_projectile_picker.py` (projectile speed). A shared `CalibrationPickerBase` will be extracted on the third instance (rule of three), not now.

Future calibrations (per ADR-005 source profile pattern, additional games) reuse the same pattern — same input contract, same handshake, same output contract.

### Module location

`apps/mame-harness/visual_jump_picker.py` — sits alongside `physics_calibrator.py` and `episode_extractor.py`, all in the harness layer that orchestrates the public-side calibration pipeline.

### Dependencies

- numpy only (already installed via opencv-python-headless)
- No new external dependency (avoided scipy.signal.find_peaks; custom peak finder is ~30 lines and fits the minimalism implied by ADR-001)

## Approach

### Capture protocol

1. User records a dedicated capture where Arthur only jumps in place (no walking, no firing, no enemies in frame). **5–10 distinct jumps**.
2. Between jumps, user waits ≥ 30 frames (clear arc separation; allows the ground streak to be unambiguous).
3. User closes MAME after the planned jump count.

### Frame extraction

4. Agent runs `./scripts/extract_frames.sh t10_7_jumps`.
5. Output: `evidence/private/run_t10_7_jumps/frames/extracted_png/*.png` + regenerated `specs/traces/gng_trace.json`.

### Anchor identification (amended)

6. Agent runs `apps/mame-harness/visual_jump_picker.py <run_id>` which:
   - Loads `specs/traces/gng_trace.json`
   - Filters player entries → builds (frame, y) signal
   - Runs custom numpy peak-finder on `−y` (since y=0 is top of screen, valleys in y = peaks in altitude) with parameters:
     - `min_distance = 30` (frames; rejects clustered noise)
     - `min_prominence = 0.05` (normalized depth; rejects micro-oscillations)
   - For each detected peak frame `P`:
     - `jump_start_frame` = last frame in `[P − 25, P − 3]` where Arthur was at a stable grounded y (within 0.01 of pre-window median)
     - `land_frame` = first frame in `[P + 3, P + 25]` where Arthur returns to a stable grounded y
   - Computes per-candidate metadata: `height_ascend`, `height_descend`, `t_ascend`, `t_descend`, `flat_ok`, `sym_ok`
   - Outputs a structured table to stdout AND writes `evidence/private/run_<id>/logs/jump_candidates.json` for ST.A4 consumption

7. Agent presents to user:
   - The candidates table (frame numbers + computed metadata + auto-validation flags)
   - Brief note: "For each row with `flat_ok=yes` and `sym_ok=yes`, open the PNG at the peak frame and confirm Arthur is visibly at the top of a jump arc. Reply with accepted candidate IDs."

8. User opens `evidence/private/run_<id>/frames/extracted_png/<peak_frame>.png` for each candidate they want to verify, and replies with a list of accepted candidate IDs (e.g. "accept 1, 2, 4; reject 3 — that's mid-fall not jump").

### Physics computation

10. For each user-confirmed (jump_start_frame, peak_frame, land_frame):
    - y_ground = trace player y-value at jump_start_frame
    - y_peak = trace player y-value at peak_frame
    - y_land = trace player y-value at land_frame
    - height_ascend = y_ground − y_peak (positive; y=0 is top of screen, y=1 is bottom)
    - height_descend = y_land − y_peak (positive; should ≈ height_ascend if Arthur landed on same flat ground)
    - t_ascend = peak_frame − jump_start_frame
    - t_descend = land_frame − peak_frame

11. Kinematic identities (parabolic arc anchored at peak):
    - From ascent: `jumpVelocity_y_per_frame = 2 × height_ascend / t_ascend`
    - From ascent: `gravity_ascend = 2 × height_ascend / (t_ascend)²`
    - From descent: `gravity_descend = 2 × height_descend / (t_descend)²` (independent estimate of gravity)

12. Per-jump validation (sanity checks for symmetric arc on flat ground):
    - **Flat-ground check**: `|y_land − y_ground| < 0.02` (≈ 4 px; rejects jumps that landed on a step/platform)
    - **Symmetry check**: `0.7 ≤ gravity_descend / gravity_ascend ≤ 1.4` (rejects arcs where descent doesn't match ascent → likely tracker noise or input lag artifact)
    - Per-jump `gravity_combined = (gravity_ascend + gravity_descend) / 2`
    - Jumps that fail either check are dropped from the median computation

13. Aggregate across valid jumps:
    - `jumpVelocity_y_per_frame = median(jumpVelocity_y across valid jumps)`
    - `gravity_per_frame_squared = median(gravity_combined across valid jumps)`

14. Convert to per-second: `× 60` for velocity, `× 3600` for gravity (60 fps assumption matches existing calibration convention).

### Update artifacts

14. `specs/calibration/gng_physics_calibration.yaml` → new `jump_velocity_y` + `gravity_units_per_frame` blocks
15. `apps/rn-prototype/src/engine/PhysicsSystem.ts` `CALIBRATED_PHYSICS_CONFIG` → new constants
16. RN engine tests verified
17. Validation gate: `|t_peak_predicted − t_peak_observed| / t_peak_observed < 0.30` where t_peak_predicted = jumpVelocity_y / gravity_per_frame_sq

## Why Kinematic Formula

For a parabolic jump arc with initial upward velocity `v₀` (in screen-y space, upward means decreasing y) and downward gravity `g`:

```
y(t) = y_ground − v₀·t + ½·g·t²
```

At peak: `y'(t) = −v₀ + g·t = 0` → `t_peak = v₀ / g`, i.e. `v₀ = g · t_peak`.

Height at peak: `h = y_ground − y(t_peak) = v₀·t_peak − ½·g·t_peak² = ½·g·t_peak²`.

Solving:
- `g = 2h / t_peak²`
- `v₀ = g · t_peak = 2h / t_peak`

### Why also confirm the land frame

The descent half of the arc is governed by the same physics (no air resistance, constant `g`). Starting from peak with `v_y=0`:

```
y(t) = y_peak + ½·g·t²
```

At land (Arthur back on ground): `h_descend = y_land − y_peak = ½·g·t_descend²`, so:

- `g_descend = 2·h_descend / t_descend²`

This is an **independent estimate** of `g` derived from a different half of the arc. If `g_ascend ≈ g_descend` we have strong evidence the parabolic model holds (no hidden gravity table, no input lag bias). If they diverge, the jump sample is rejected as noise.

With two-point anchoring (peak only) we have one estimate of `g`. With three-point anchoring (peak + land) we get a free cross-validation.

## Risks

- **R1 — User picks non-peak frame (subjective error)**: Mitigation: agent surfaces 3–5 frames around the kinematic peak estimate; user picks the maximum among them. Sub-frame precision is not necessary at 60 fps resolution.
- **R2 — Few jumps yield poor median**: Mitigation: require ≥ 5 **valid** jumps (after flat-ground + symmetry validation) as acceptance criterion.
- **R3 — Trace lacks player entry at user-confirmed frame**: Mitigation: agent falls back to nearest frame ± 1; if still missing, asks user to pick an adjacent frame.
- **R4 — Jump button mapping differs from expectation**: Mitigation: agent inspects `input_plan.json` structure before assuming `BUTTON1` is jump; uses whichever non-empty button activates Arthur ascending in trace.
- **R5 — User's recorded jumps land on stairs/platforms (variable y_ground)**: Mitigation: user instructed to stay on flat ground; agent rejects jumps where `|y_land − y_ground| > 0.02` (≈ 4 px).
- **R6 — Asymmetric arc (descent gravity disagrees with ascent)**: Mitigation: agent rejects jumps where `gravity_descend / gravity_ascend` is outside `[0.7, 1.4]`. Could indicate input lag, frame skip, or partial occlusion at peak. Drops the sample rather than corrupting the median.

## Reasoning Grade

`Medium`

Reasoning basis:
- Bypasses an architectural issue (entity-id-collision) instead of solving it — a deliberate scope decision, not a hack
- Human-in-loop adds a confirmation step but reduces overall risk vs. another round of tracker debugging
- Cross-module impact is contained: trace structure unchanged, only calibration values + RN constants change

## Effort Grade

`M`

Effort basis:
- User capture: ~5 minutes
- Agent processing: candidate identification, file path listing
- Multiple round-trips for user confirmation
- Final calibration computation is straightforward
- Test verification is mechanical
