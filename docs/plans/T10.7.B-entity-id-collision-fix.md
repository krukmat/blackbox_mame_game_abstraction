# T10.7.B — Entity-ID Collision Fix (Plan)

## Status

Proposed — awaiting explicit approval. Blocks T10.7.A ST.A3b (visual validation needs clean candidates).

## Objective

Eliminate the entity-id collision in `packages/vision/trace_extractor.py` where non-Arthur blobs with player-sized area get assigned `entity_id="player"`, producing duplicate player entries per frame that corrupt downstream physics calibration.

## Why Now

T10.7 ST3 diagnostic and T10.7.A ST.A3a execution both surfaced the same root cause:

- ST3 diagnostic on `run_t10_4_01`: 85 frames had two `entity_id="player"` entries each, producing spurious `jump_start` events that prevented the `< 30` gate.
- ST.A3a picker run on `run_t10_7_jumps`: only 4 candidates detected (vs the 8 jumps the user performed), with implausible values for the survivors (candidate #2 reported H=0.44, physically impossible).

Both observations trace to the same bug. Fixing it unblocks ST.A3b (re-run picker on same capture → cleaner candidates → user validation → ST.A4 calibration).

Without this fix, T10.7.A would either:
- Settle for very few low-confidence calibration samples (degrading the final physics constants), or
- Require a re-capture session with the same bug still present (same underlying corruption, just more samples).

## Root Cause Analysis

In `packages/vision/trace_extractor.py`:

```python
def _entity_type_from_box(region, frame_width, frame_height) -> str:
    ratio = (region.width * region.height) / (frame_width * frame_height)
    if ratio >= _RATIO_PLAYER:
        return "player"
    ...

def _entity_id_from_type(entity_type, frame, region_index=0) -> str:
    if entity_type == "player":
        return "player"   # ← collision: any "player"-typed region collapses to entity_id="player"
    ...
```

In `extract_trace`:

```python
player_region = tracker.find_arthur(curr_stat.changed_regions, sig)
if player_region is not None:
    regions_to_emit.append(("player", "player", player_region))

remaining_regions = _regions_except_claimed(curr_stat.changed_regions, player_region)
for region_index, region in enumerate(remaining_regions):
    entity_type = _entity_type_from_box(region, frame_width, frame_height)
    # ↑ remaining_regions can include blobs the same size as Arthur (e.g. boss limb,
    #   large enemy, scenery glitch). Those get entity_type="player".
    entity_id = _entity_id_from_type(entity_type, curr_stat.start_frame, region_index)
    # ↑ entity_id becomes "player" → collides with the real Arthur entry above.
    regions_to_emit.append((entity_id, entity_type, region))
```

Result: in any frame where a non-Arthur blob is also player-sized, the trace contains two `entity_id="player"` entries. Each tracks its own state history independently and can emit its own `jump_start` events. The `MIN_GROUND_STREAK` debounce (ST2) is keyed per-entity-id and cannot distinguish the two.

This violates the implicit contract that `entity_id="player"` is reserved for the `ArthurTracker.find_arthur` result.

## Design Decision

Add an `allow_player` flag to `_entity_type_from_box`:

```python
def _entity_type_from_box(
    region: MotionBox,
    frame_width: int,
    frame_height: int,
    allow_player: bool = True,  # T10.7.B: False when player slot is already claimed
) -> str:
    ratio = (region.width * region.height) / (frame_width * frame_height)
    if allow_player and ratio >= _RATIO_PLAYER:
        return "player"
    if ratio >= _RATIO_ENEMY_A:
        return "enemy_a"
    if ratio >= _RATIO_PROJECTILE:
        return "projectile"
    return "hazard"
```

In `extract_trace`, the two call sites that process **remaining_regions** (the disappearance peek loop AND the main emission loop) pass `allow_player=False`. The single call site for the candidate selection (where Arthur has not yet been resolved) keeps `allow_player=True` (default).

### Why a flag, not a separate function

- Single source of truth for the area-ratio thresholds
- Backward-compatible default (existing callers unaffected)
- Minimal API surface change
- Tests can exercise both branches with one helper

### Why not modify `_entity_id_from_type`

The collision is upstream — by the time `_entity_id_from_type` runs, the wrong `entity_type` is already assigned. Fixing at `_entity_type_from_box` prevents the bad classification rather than masking it downstream.

## Affected Files

### Modified
- `packages/vision/trace_extractor.py` — add `allow_player` parameter + update two callsites
- `packages/vision/tests/test_trace_extractor_multi.py` (or a new dedicated test file) — regression tests for the collision fix

### Regenerated (artifacts, not hand-edited)
- `specs/traces/gng_trace.json` — re-extracted from `run_t10_7_jumps` after the fix lands

### Documentation
- `CLAUDE.md` / `AGENTS.md` Known Gaps — add then resolve entry referencing ADR-012
- `docs/obsidian/Vision Layer.md` — note the fix
- `docs/tasks/gng_source_integration/T10.7-tracker-continuity-fix.md` — add T10.7.B subtask reference
- `docs/tasks/gng_source_integration/T10.7.A-visual-calibration.md` — mark ST.A3b as blocked on T10.7.B

## Module Dependencies

```
extract_trace (caller)
    └─> _entity_type_from_box  ← change here (add allow_player flag)
         └─> ratio thresholds (unchanged)
extract_trace (caller again, for remaining_regions)
    └─> _entity_type_from_box(allow_player=False)  ← new behavior
```

No public schema change. No ADR boundary change.

## Out of Scope

- Multi-entity tracking continuity for enemies (different problem; ADR-013 Known Gap)
- MOG2 scroll reset on stage transitions (ADR-013 Known Gap, deferred to T12 prep)
- Generic multi-game player tracker abstraction
- Changes to `ArthurTracker` (ST1 covered the velocity ceiling)
- Changes to `_infer_events` (ST2 covered the ground-streak debounce)
- Schema changes to trace JSON output
- New evidence capture run (the existing `run_t10_7_jumps` frames are sufficient)

## Risks

- **R1 — Legitimate player-sized enemies misclassified as `enemy_a`**: Mitigation: this is the desired behavior. The intent was always that `entity_id="player"` means Arthur; large enemies belong in `enemy_a`. The current bug is the regression.
- **R2 — Other consumers depend on the buggy behavior**: Mitigation: search the codebase for code that expects multiple `entity_id="player"` entries per frame. None found in initial survey; regression tests will catch any.
- **R3 — Trace regeneration produces fewer downstream events**: Mitigation: this is expected and intended. The picker run on the cleaner trace should produce fewer but more reliable candidates.
- **R4 — Fix does not resolve all picker noise**: If after T10.7.B the picker still emits noise candidates, document residual sources but do not block T10.7.A on further detector improvements — user visual validation absorbs residual noise.

## Validation Gate

T10.7.B is complete only when:

1. All existing `packages/vision/tests/` tests pass (71 currently).
2. New regression tests cover the `allow_player=False` behavior.
3. Re-extracted `specs/traces/gng_trace.json` from `run_t10_7_jumps` has **zero frames with duplicate `entity_id="player"` entries**.
4. Re-run of `visual_jump_picker.py t10_7_jumps` produces candidates whose `H_asc` values are all `< 0.10` normalized (physically plausible — Arthur's screen height is ~0.10).

## Reasoning Grade

`Medium`

Reasoning basis:
- Cross-module impact contained: change in `trace_extractor.py`, regenerated artifact downstream
- Root cause identified and reproduced; fix is direct
- Risk of breaking existing consumers exists but is mitigated by regression tests

## Effort Grade

`S`

Effort basis:
- Single parameter addition + two callsite updates: < 15 lines of production code
- 3–4 regression tests
- Trace regeneration is mechanical
- No new dependencies
